# PMW HR Forms — si-cmms design overhaul

Status: approved design, not yet implemented
Date: 2026-09-05

## Goal

Rebuild PMW HR Forms so it reads as si-cmms' sibling and behaves like an
application rather than a long page: a persistent menu of categories, each
opening its own strip of sub-sections, with every destination reachable from the
chrome instead of from a hamburger menu.

Two things are being changed at once, deliberately, because they are the same
change: the visual system, and the information architecture that system exists
to express.

## Decisions taken

| Question | Decision |
|---|---|
| How far the si-cmms look goes | Full palette — navy, amber, green, red on the flat canvas |
| Which surfaces | All of them: staff app, form builder, public careers portal |
| Menu shape | Navy sidebar on desktop, fixed bottom bar on phones |
| Navigation depth | Two levels: sidebar categories, top tab strip within each |
| Delivery | One rewrite, landing as a single change |
| Dashboard background picker | Kept, retuned to navy-family tints, flat canvas as the default |

Delivery was chosen against the recommendation in this document's brainstorming
(a token-first surface-by-surface migration). The recommendation was made, the
decision was the user's, and this spec plans the single-landing rewrite. The
consequence to hold in mind: nothing is reviewable until the whole change is
done, so the verification section below is load-bearing rather than a formality.

## 1. Navigation

### The map

Five categories. Every existing route is placed; none is dropped.

| Category | Tabs | Routes |
|---|---|---|
| Dashboard | — | `/admin/dashboard`, `/user/dashboard` |
| My Work | Forms · My Submissions · Approvals | `/admin/submissions`, `/admin/approvals` |
| Internal Portal | Job Portal · Learning | `/career-portal`, `/learning` |
| Admin | Form Builder · Routing · Organisation · Jobs · Learning · Guests · Portal Cards · Career Applications | `/admin/builder`, `/admin/routing`, `/admin/org`, `/admin/jobs`, `/admin/learning`, `/admin/guest-members`, `/admin/career/cards`, `/admin/career/applications` |
| Profile | My Profile · Appearance · Privacy Notice | `/privacy`, plus `/profile` and `/profile/appearance` (new) |

### URLs do not change

This is a hard constraint, not a preference. Approval notification emails link
to `/approval/:token`. Prefilled QR codes generated by `PrefilledQrPanel` point
at `/form/:formId`. Evaluators receive `/eval/...` links. Those links live in
people's inboxes and on printed codes, and re-slugging routes would break them
silently — the failure would surface as an approver reporting that a link "does
nothing", weeks later, with nothing connecting it to this change.

Therefore categories and tabs are a **presentation layer derived from the current
path**, not a new routing scheme. `/admin/*` stays `/admin/*`. New routes may be
added — the Profile section needs two — but no existing path moves or changes
meaning.

### Configuration

One module, `src/config/navigation.ts`, holds the categories, their tabs, the
icons, the role gating, and the path-to-category resolution. Nothing else knows
the shape of the menu. The reason for a single module rather than props threaded
through the shell: the same map is needed by the sidebar, the bottom bar, the tab
strip, and the redirect that decides where a signed-in user lands. Four
consumers of one fact is exactly when that fact needs one home.

Role gating in that module must agree with the route guards in `App.tsx`. A tab
an account cannot open must not be drawn — offering a link that redirects
straight back is the same "nothing works and nothing says why" that a guard is
supposed to prevent.

### Shell layout

New directory `src/components/shell/`. Pages stop drawing their own chrome:
`AdminHomePage.tsx` currently imports `Header` itself, which is why navigation
is duplicated into every page that wants it.

**Desktop, ≥1024px.** Navy sidebar on the left, 224px, full height, sticky,
carrying the `si-navy` gradient and its slow amber/blue sheen. Five category
buttons, active one filled in mid-navy `#1E4FA0`. Identity block at the bottom:
name, roles, Sign out. To its right a white sticky top bar holding the active
category's tab strip, then the canvas.

**Phone, <1024px.** No sidebar and no drawer. A fixed navy bottom bar carries
the five categories as icon-and-label buttons, padded past the gesture pill with
`env(safe-area-inset-bottom)`. The tab strip sits beneath a slim top bar and
scrolls horizontally with the scrollbar hidden. Main content carries bottom
padding so the last row of a list is never trapped under the bar.

The 1024px switch is CSS, not a JavaScript width check, so there is no flash of
the wrong layout on first paint.

**Accessibility requirements**, carried over from si-cmms' shell because it
learned them the hard way:

- A skip link to `#main-content`, visible on focus.
- The main region takes `tabIndex={-1}` and is keyed on the path so the entrance
  animation replays on navigation — on a phone it is the only cue that the
  content changed.
- Every nav item and the bottom-bar buttons clear a 44px touch target.
- Focus is visibly ringed on every interactive element, no exceptions for quiet
  controls.

### Screens without the shell

The standalone form-fill pages (`/form/:formId`, `/native/:formId`), the approval
and evaluation links, and the careers portal *when reached by someone who is not
signed in*. These serve people with no sections to move between; a five-category
menu would offer four buttons that bounce to a login screen.

`/career-portal` is the one route that appears in both worlds, and it must
resolve one way or the other rather than being described twice:

- **Signed in** — it renders inside the shell, as the Job Portal tab of Internal
  Portal, and the shell supplies the chrome.
- **Not signed in** — it renders bare with its own top bar, exactly as today.

The shell decides this from the existing auth state, not from a separate route.
Signed-in staff browsing internal openings should not lose the menu they were
just using, and an external applicant must not be shown one.

## 2. Design system

`src/theme/editorial.ts` keeps its name and its exported symbols so the 48 files
importing it keep compiling. Every value inside changes. The `--pmw-*` variables
in `src/index.css` change in lockstep; they are the same facts expressed twice
and must not drift.

### Colour mapping

| Role | Today | Becomes |
|---|---|---|
| Brand, actions, links, focus, active nav | `#0078D4` | navy `#0F3D91` |
| Brand dark | `#005A9E` | `#0B2F70` |
| Brand mid (active nav fill) | — | `#1E4FA0` |
| Page background | sky→cream gradient | flat canvas `#F6F8FB` |
| Ink | `#101010` | `#101828` |
| Secondary text | `#5F646D` | `#5A6880` |
| Border | `#D6DCE5` | `#E5E9F0` |
| Attention accent | yellow `#FFF546` | fill `#F59E0B`, text `#9D6507`, soft `#FDE7C4` |
| Success | `#107C10` | fill `#22C55E`, text `#178640` |
| Error | `#C62828` | fill `#EF4444`, text `#C1291F` |

### The two-value semantics

Amber, green and red each carry two values, because one hue cannot be both a
bright fill and readable text. Measured as text on white: `#F59E0B` is 2.15:1,
`#22C55E` is 2.28:1, `#EF4444` is 3.76:1 — all three fail 4.5:1, and all three
carry the status words a submissions list exists to convey.

Rule: `*.text` variants for words, DEFAULT for fills, dots, borders and icons.
This is not stylistic. A "Rejected" badge whose text is the bright red is
unreadable for a meaningful share of users.

### Purple retires

`pmwPurple` appears 71 times as the admin/secondary accent — role badges,
learning topic cards, the carousel, the submissions toolbar, the detail modal.
si-cmms has no purple; its secondary signal is amber. Each of the 71 sites
resolves to one of two things: amber where the colour carried meaning
(secondary emphasis, admin distinction), or plain navy where it was decorative.
The distinction is decided per site, not swept globally — a decorative purple
turned amber adds a false signal.

### The long tail

188 distinct hex values across 860 occurrences in `src/**/*.{ts,tsx}`. Around
140 of the distinct values are one-off greys and washes duplicating a token
badly: `#6B7280` (71 uses), `#9CA3AF` (35), `#374151` (11) and `#D1D5DB` (7) are
four different greys doing one job in different files.

All 860 occurrences become token references. This is the bulk of the mechanical
work and the main reason a single-landing rewrite is large. A raw hex left behind
is a screen that did not get overhauled, so the completion criterion is
measurable: no literal hex colours in `src/**/*.{ts,tsx}` outside
`theme/editorial.ts`, `components/builder/builderTheme.ts`, and the background
gallery definitions.

### Shape and type

Already ported and unchanged: the 12px container radius, 5px badge radius, the
single card shadow, the raised-surface shadow, the `siType` scale, the focus
ring. The focus ring's comment ("PMW has no amber, so the ring is PMW blue")
becomes stale once amber arrives; the ring stays navy, because navy is what
"about to act on" now means in this app, and the comment is corrected to say so.

### Dashboard background picker

`BackgroundPicker.tsx`, its gallery in `utils/dashboardBackgrounds.ts`, the
SharePoint-stored setting and the `--app-bg` variable all survive.

Changes: flat canvas `#F6F8FB` becomes the default selection, and the gradient
presets are retuned to navy-family tints so a chosen background sits under
si-cmms cards without clashing. The `DEFAULT_FALLBACK` gradient in
`dashboardBackgrounds.ts` and the six inline copies of the old gradient string
(in `App.tsx`, `AdminGuard.tsx`, `ChoiceScreen.tsx`, `GuestLanding.tsx`,
`careerUi.tsx`, `learningUi.tsx`, `AdminHomePage.tsx`) all resolve to the canvas.

Those inline duplicates are themselves a defect: seven copies of one gradient,
already drifted into three variants. They collapse to one token.

## 3. Content

### Dashboard

Overview only. Stat tiles redrawn as si-cmms `StatCard`s — flat white, 12px
radius, one shadow, a micro uppercase label over a tabular-figure number — plus
a compact "needs your attention" strip and the careers carousel. The filter
toolbar and the submissions list move out.

### My Work → Forms

Takes over what `ListSummaryCards.tsx` does today: the forms this account can
fill, as a card grid. Navy title, count as tabular data, amber "Fill in" as the
primary action, Edit shown only to form-builder users.

### My Work → My Submissions

Takes the filter toolbar, list header and rows. Rows keep their current
information and adopt si-cmms row metrics: 44px single-line, 52px once a row
carries two lines. Status becomes a 5px-radius badge in the darkened semantic
text colours, never the bright fills.

### My Work → Approvals

`/admin/approvals`, behaviour unchanged.

### Internal Portal, Admin

Existing pages, each losing its own header and gaining the shell's tab strip.

### Profile

New as a destination; identity currently lives in the header menu. Gathers name,
roles, company, the appearance setting, and the privacy notice.

### Carousel cards

`CareerPortalCarousel.tsx` keeps the concept — a horizontally scrolling row of
admin-authored image cards, each targeting a job or URL. The skin changes: 12px
radius, the single card shadow, si-cmms type, amber call-to-action. The three
system-default cards' colours move to the navy family.

**Data caveat.** Each card's `colorStart`, `colorEnd` and `colorAccent` are
stored per card in SharePoint, and existing rows hold blue→purple gradients.
Defaults can change; rows an admin already authored cannot, without writing to
the live list. After this ships, existing carousel cards render in their stored
blue and purple until someone re-picks their colours in the Portal Cards admin
screen. This is expected, not a missed spot.

## 4. Form builder

Less work than `DESIGN.md` implies. `builderTheme.ts` already uses Inter (not the
Public Sans that DESIGN.md still claims), and its `shadowSm`/`shadowMd`/
`shadowLg` are byte-identical to si-cmms' card and raised elevations. Its
8px-inner / 12px-container geometry is si-cmms' too.

Three changes:

1. The `accent` family (`accent` through `accent900`, `#0078D4`→`#0A3050`)
   becomes the navy family.
2. The desk greys (`bg` `#F2F4F7`, `surface` `#E7EBF0`, `panel` `#F7F9FB`)
   become the canvas family.
3. The navy mode rail carrying Build · Flow · Settings · Publish adopts the same
   `si-navy` gradient and sheen as the sidebar, so rail and sidebar read as one
   surface rather than two different navies meeting at a corner.

`builderTheme.ts` and the `--bx-*` variables in `BuilderShell.css` change
together — that file's own comment warns they must.

**Kept intact:** the builder's layout thesis. Two panes at most, the form sheet
centred on a sunken desk, properties docked only while a field is selected. That
is a considered answer to a real problem — a crowded authoring screen — it does
not conflict with si-cmms, and discarding it would cost a working tool to gain
nothing visual.

## 5. Public careers portal

Full palette, per the scope decision. The hero's blue-to-purple wash becomes
navy, job cards take the standard card treatment, the apply form matches internal
form styling. The portal keeps its own top bar rather than the sidebar, since an
applicant has no sections to move between.

Noted at decision time and recorded here: job applicants will see the navy of an
internal maintenance tool rather than a recruitment-marketing look. This was
chosen deliberately.

## 6. Documentation

`DESIGN.md` is rewritten, not left behind. It currently describes two visual
worlds and a Public Sans decision that is no longer true. After this change it
describes one system. A design document that contradicts the code is worse than
none, because the next reader trusts it.

`CONTEXT.md` is updated where it describes navigation or visual structure.

## 7. Verification

### Gates, in order

1. **`npm test`** — 56 test files, covering logic: routing plans, layer
   validation, PDF formatting, expression evaluation. None asserts a colour, so
   this change should not touch them. A newly failing test is a genuine
   behavioural regression, not a cosmetic diff.
2. **`npx tsc -b`** run on its own, not via `npm run build`. The deploy build
   compiles under different globals than a plain dev typecheck, so a change that
   builds locally can still fail on Vercel.
3. **Browser verification** of the running app, performed rather than delegated
   to the user: the shell at desktop width, at 1024px where the sidebar hands
   over to the bottom bar, and at 360px; a pass through all five categories and
   every tab, checking for console errors and horizontal overflow.
4. **Contrast check on the new palette.** si-cmms' own token file records getting
   this wrong first time round. Each new semantic colour is measured as text
   against the canvas before shipping, not after.

### What cannot be verified here

Anything behind SharePoint or Microsoft sign-in. The tenant is unreachable from
this environment, so the submissions list, approval chains, org directory and the
carousel's live cards render only in their dataless states. Empty and loading
states get careful attention, and the completion report states explicitly which
screens were seen with real data and which were not.

### Mechanical constraints

- Source files are CRLF. Multi-line exact-match edits break unless line endings
  are preserved.
- System `python` is 2.7. Patch scripts use `python3`, or non-ASCII content dies.
- A heredoc'd patch script loses one level of backslash escaping; prefer written
  script files over heredocs for anything with escapes.

## Out of scope

- Any change to SharePoint list schemas or stored data.
- Behavioural changes to approval routing, PDPA handling, or PDF generation.
- Migrating existing carousel card colours in the live list (see the caveat in §3).
- Dark mode. si-cmms does not have one; adding one here would be inventing a
  system rather than adopting one.
